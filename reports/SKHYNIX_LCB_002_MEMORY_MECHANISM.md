# Luna L1 기억과 제출 형식의 연결 기록

2026-09-24. 완료된 Luna/low 파일럿의 VALID 24쌍을 읽기 전용으로 분석했다. **실제로 전달된 L1 기억에 유효한 제출 회고의 정수 목록 예시가 있었고, 개선된 10문제 모두 그 기억을 같은 세션에서 받은 뒤 첫 `finish`를 유효한 형식으로 제출했다.** 따라서 기억이 제출 형식의 예시를 제공했다는 경로는 확인됐다. 그 예시만이 성공을 유발했다는 독립적인 인과 효과를 측정한 실험은 아니다.

새 모델 호출·채점·검색·메모리 쓰기·원본 변경은 없다. [본평가 보고서](SKHYNIX_LCB_002_LUNA_EVALUATION.md)의 OFF 12/24, ON 22/24와 별도인 사후 기록 분석이다. 추가한 실패 경험 15건은 이 실행에 쓰이지 않았다.

## 기억에 실제로 들어 있던 정보

TRAIN에서 저장한 L1은 모델이 작성한 `source_lesson` 전체를 JSON 문자열로 보존했다. 여기에는 알고리즘 경험 문장뿐 아니라 `trace_steps` 필드도 포함됐다. 검색 후 모델에 전달하는 `exact_text`에도 이 JSON이 그대로 포함됐다. 즉 정수 목록이라는 형식 예시가 경험의 구조에 들어 있었다.

```text
TRAIN source_lesson
  → L1 episode.summary에 trace_steps 포함
  → exact_text의 중첩 JSON에 보존
  → 세션 prompt 또는 앞선 도구 응답의 context.memory
  → 이후 finish 요청의 trace_steps를 관측
```

실제 은행의 L1 9건 중 7건이 사용됐고, 23문제에 총 36건의 주입이 있었다.

| 출처 TRAIN 문제 | 기억 속 정수 예시 | 주입 건수 |
| --- | --- | ---: |
| `abc311_b` | `[2]` | 4 |
| `abc347_a` | `[2]` | 5 |
| `abc375_a` | `[2]` | 7 |
| `2848` | `[2]` | 14 |
| `3379` | `[2]` | 2 |
| `abc318_d` | `[2]` | 2 |
| `abc327_a` | `[11]` | 2 |

예를 들어 출처 `2848`의 중첩 JSON을 펼치면 `{"trace_steps": [2]}`가 있다. 이는 출처 문제의 실행 번호다. 대상 문제는 자신의 유효한 실행 번호를 사용해야 한다. 같은 `[2]`가 두 문제에 나타나는 것만으로 숫자를 복사했다고 판정할 수 없다.

경험의 summary·applicability·procedure 문장에 대한 8개 문자열 검색에서는 `trace_steps`, `source_lesson`, `finish`, `submit`, `submission`, `integer`, `format`, `schema`가 발견되지 않았다. 이 검색만으로 의미상 형식 조언이 전혀 없었다고 결론내리지 않는다. 확인된 핵심은 **구조화된 정수 예시 자체가 전달됐다는 점**이다. [출처·형식 근거](../artifacts/skhynix_v1/lcb_002/mechanism-001/memory-examples-001.json).

## 미제출에서 성공으로 바뀐 10문제

아래 10개는 OFF에서 미제출, ON에서 제출·정답 성공이었다. 모두 ON의 첫 `finish`가 승인됐고, 그 요청 시작보다 앞선 같은 세션의 도구 응답에 기억이 있었다. 단순히 최종 은행에 저장돼 있었다는 사실을 노출 증거로 사용하지 않았다.

| 대상 문제 | 같은 제출 세션에서 먼저 전달된 출처와 예시 | ON 제출 값 |
| --- | --- | --- |
| `abc382_f` | `2848` `[2]` | `[4]` |
| `abc378_e` | `3379` `[2]` | `[2]` |
| `abc381_d` | `2848` `[2]` | `[2]` |
| `abc384_f` | `2848`, `abc375_a` 각각 `[2]` | `[2]` |
| `3620` | `abc318_d` `[2]` | `[3]` |
| `abc380_e` | `abc311_b` `[2]` | `[3]` |
| `abc381_c` | `abc327_a` `[11]`, `abc375_a` `[2]` | `[2]` |
| `abc378_b` | `2848` `[2]` | `[2]` |
| `3659` | `2848`, `abc375_a` 각각 `[2]` | `[2]` |
| `3626` | `abc347_a` `[2]` | `[3]` |

예를 들어 `abc382_f`는 OFF에서 문자열·객체를 담은 목록으로 제출해 거부됐다. ON에서는 출처 `2848`의 `[2]` 예시를 도구 응답으로 먼저 받은 뒤, 자기 실행 기록의 `[4]`를 넣어 승인됐다. 출처 번호와 대상 번호가 다른 이 사례는 원본 숫자를 그대로 복사한 결과가 아니며, 유효한 정수 목록 형식을 사용하는 행동과 일치한다. 모델이 그 형식을 선택한 내부 이유까지 직접 관측한 것은 아니다.

이 10개는 OFF의 실패 상태를 ON이 이어받아 수정한 실험이 아니다. 같은 문제를 각각 독립적으로 푼 비교다. 별도로 OFF에서 제출 오답이었고 ON에서 정답이 된 `3631`도 첫 `finish` 전에 기억을 받았지만, 미제출 개선 10개에 섞지 않는다.

## 실제로 형식을 수정한 사례와 실패 사례

`abc380_d` ON에서는 한 실행 안의 수정 과정도 관측됐다.

1. 세션 1에서 `abc311_b`의 `[2]` 예시를 받았다.
2. 세션 2의 `finish` step 5~8에서는 문자열·문자열·객체·문자열 목록으로 네 번 거부됐다. 해당 세션의 prompt와 앞선 도구 응답의 구조화된 `context.memory`는 비어 있었다.
3. 세션 3에서 `abc347_a`의 `[2]` 예시를 받았고, 공개 테스트 step 10의 응답에도 같은 기억이 있었다.
4. 이후 step 11의 `finish`가 대상 기록에 존재하는 정수 목록 `[10]`으로 승인됐다.

이 기록은 “형식 거부 → 새 세션의 형식 예시 전달 → 유효한 형식 제출”이라는 순서를 보여준다. 동시에 새 세션·새 공개 테스트·다른 기억이 함께 바뀌었으므로 특정 기억 하나의 독립 효과로 분리하지 않는다.

반대 사례도 유지했다. `3636` ON은 세션 1의 초기 prompt에 `abc327_a`의 `[11]` 예시가 있었지만, 실제로 8번 제출한 세션 2의 선행 구조화된 기억은 없었다. 제출은 문자열·객체·빈 목록 또는 회고 누락으로 실패했으며 정수 `11`을 제출한 기록은 없다. `abc386_c`는 기억 주입 자체가 없고 양쪽 모두 미제출이었다.

## 전체 제출 시도와 증거의 강도

VALID의 모든 48개 실행, 68개 native 세션을 분석했다. OFF는 `finish` 184회 중 승인 13회·거부 171회, ON은 40회 중 승인 22회·거부 18회였다. 반복 요청을 모두 보존했다.

| ON의 제출 요청 직전 같은 세션에 구조화된 기억 전달 기록 | 승인 | 거부 |
| --- | ---: | ---: |
| 있음 | 22 | 0 |
| 없음 | 0 | 18 |

여기서 **40회는 독립적인 40문제가 아니라 24문제에서 나온 제출 요청 수**다. 이 표로 독립 시행의 효과 크기나 유의확률을 계산하지 않는다. “없음”은 직접 전달된 `context.memory` 항목이 없다는 뜻이며, 이전 기억이 L0 문맥이나 인계 설명에 재서술됐을 가능성까지 배제하지 않는다.

주입 36건 중 27건은 원래 session receipt가 기록한 events 해시까지 연결되는 도구 응답에서 확인했고, 나머지 9건은 저장된 초기 prompt에서만 확인했다. 원래 receipt는 prompt 해시를 저장하지 않았으므로 후자는 분석 시점 해시와 동결 실행 코드의 prompt→stdin 경로에 근거한다. 원래 실행 시점에 독립적으로 봉인된 prompt라고 표현하지 않는다.

승인된 ON 22건 중 20건은 같은 세션의 선행 도구 응답으로도 기억 전달이 확인된다. 나머지 `3653`, `abc379_b` 2건은 저장 prompt가 선행 전달 근거다. 특히 미제출→성공 10개는 모두 원래 events 해시가 연결되는 선행 도구 응답 근거가 있다. `finish` 자신의 응답에서 발견한 기억은 해당 제출에 앞선 노출로 세지 않았다.

[전체 전달·제출 순서](../artifacts/skhynix_v1/lcb_002/mechanism-001/timeline-002.json)는 요청 시작과 앞선 응답 완료의 로그 순서를 사용한다. 주입별 시각은 원래 없으므로 만들어 넣지 않았다. 상태·출처·세션·events·기억 텍스트의 해시를 연결하고 분석 전후 원본 불변을 확인했다. 문제·코드·테스트·경험 문장·모델 내부 추론은 보고서에 포함하지 않는다.

## 해석과 후속 검증의 경계

이 로그 분석으로 근거가 있는 설명은 **“L1 경험이 유효한 회고 형식의 예제를 제공했고, 실제 제출 전에 그 예제에 노출된 ON 실행에서 올바른 형식의 제출이 관측됐다”**다. 형식 예시가 제출 성공을 도왔다는 설명은 이 로그와 부합한다. 이 원래 실행만으로 같은 기억의 알고리즘 경험, 세션 전환, 추가 작업의 영향을 분리하지는 않는다.

정확한 기여를 분리하려면 형식 예시만 제공하는 조건과 경험 문장은 유지하되 해당 예시를 제거하는 조건 등을 같은 규약에서 반복 비교해야 한다. `summary.trace_steps`뿐 아니라 `actions.step_no`에도 숫자 예시가 있으므로 일부 필드만 지웠다고 형식 단서 전체를 제거했다고 가정할 수 없다.

2026-09-24 후속 [제출 형식 통제 실험](SKHYNIX_LCB_FORMAT_ABLATION.md)을 완료했다. 24문제의 동일 코드·공개 기록을 두 조건의 새 세션에 주고 3회씩 비교했으며, 두 예시 필드를 유지한 조건은 원본 코드 보존·첫 제출 성공 63/70(90.0%), 삭제 조건은 0/72였다. 유지 조건 2건은 기록 오류로 null이다. 이는 고정된 제출 단계에서 형식 예시의 기여를 분리한 근거이며, 원래 전체 문제풀이 성적 차이를 모두 이 효과로 돌리는 것은 아니다.

재현 방법과 콘텐츠 노출 경계는 [분석 도구 안내](../artifacts/skhynix_v1/lcb_002/mechanism-001/README.md)에 정리했다.
