# Luna 제출 형식 예시 통제 실험

후속 검증: [양쪽에 완전한 제출 규칙을 준 전체 풀이 실험](SKHYNIX_LCB_003_EXPLICIT_FORMAT.md)을 완료했다. 양쪽 모두 첫 제출 형식 24/24 통과, 공식 정답은 OFF 24/24·ON 22/24였다. 아래의 KEEP/DROP 결과는 불완전한 공통 안내 아래 제출 형식 예시의 기여를 측정한 별도 실험이다.

2026-09-24 완료. **형식 예시 유지(KEEP)는 63/70건(90.0%), 삭제(DROP)는 0/72건이 원본 코드를 그대로 보존하며 첫 제출에 성공했다.** KEEP의 2건은 기록 저장 오류로 미확정(null)이며 본 분모에서 제외했다. 기존 OFF 12/24, ON 22/24 성적은 변경하지 않는다.

동일한 코드·공개 작업 기록·새 세션·제출 지시에서 형식 예시 필드의 유무만 바꾼 3회 반복에서 차이가 재현됐다. 따라서 이 조건에서 **L1 경험의 제출 형식 예시가 제출 규약 준수에 기여한다는 통제 실험 근거**가 생겼다. 전체 메모리 구조의 알고리즘 문제 해결률 효과나 기존 +41.7%p 전체를 설명하는 수치로 확장하지 않는다.

## 실행 결과

모델은 `gpt-5.6-luna / low`, 대상은 기존 VALID 24문제다. 두 조건을 각 3회, 총 144개 새 세션으로 실행했다. 실제 실행 시각은 **2026-09-24 11:44:58~12:12:59 KST, 28분 00초**다. 모델 요청 seed는 고정하지 못한다. 이후 검증·집계·결함 진단 시간은 이 실행 시간에 포함하지 않는다.

| 지표 | 예시 유지 KEEP | 예시 삭제 DROP |
| --- | ---: | ---: |
| 계획된 세션 | 72 | 72 |
| 성적 관측 / 미확정 | 70 / 2 | 72 / 0 |
| 첫 제출 형식 통과 + 원본 코드 보존, 주 지표 | **63/70 (90.0%)** | **0/72 (0.0%)** |
| 첫 제출 형식 통과 | 64/70 (91.4%) | 0/72 (0.0%) |
| 원본 코드 보존 | 68/70 (97.1%) | 69/72 (95.8%) |

형식은 통과했지만 코드를 바꾼 KEEP 1건은 주 지표에서 실패다. 정상 종료했으나 제출 도구를 호출하지 않은 KEEP 1건도 실패에 포함했다. 기록 오류 2건을 점수 실패나 성공으로 임의 변환하지 않았다.

| 반복 | KEEP 주 지표 | KEEP 형식 통과 | DROP 주 지표·형식 통과 | KEEP 미확정 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 21/24 | 21/24 | 0/24 | 0 |
| 2 | 21/23 | 22/23 | 0/24 | 1 |
| 3 | 21/23 | 21/23 | 0/24 | 1 |

문제마다 같은 가중치를 주고 양쪽이 관측된 반복쌍만 비교하면 주 지표 차이는 **+90.28%p**, 문제 단위 bootstrap 95% 구간은 **+79.17~+98.61%p**다. 24문제에서 70개 유효 반복쌍을 사용했다. 이는 고정된 개발 표본에서의 탐색적 구간이며, 144세션을 독립된 144문제로 취급하지 않았다. 관측률 90.0%와 문제별 평균 차이 90.28%p는 미확정의 가중치 처리 때문에 조금 다르다.

23문제에서 KEEP의 주 지표가 높았고, 1문제는 동일했다. 동일한 1문제는 기억이 전혀 없었던 대조군 `abc386_c`다. 이 문제는 두 조건의 prompt가 동일하며 양쪽 모두 0/3이었다. 기억이 있는 23문제만의 문제별 평균 차이는 +94.20%p다. **전체 24문제 결과가 주 비교이며 이 부분집합 수치로 대체하지 않는다.**

## 실제 형식 실패의 차이

DROP의 72건은 모두 제출을 시도했다. `trace_steps`를 객체 목록으로 쓴 경우 46건, 문자열 목록 15건, 필드 누락 11건이었다. 유효한 정수 목록은 0건이었다. KEEP에서 형식 검증을 통과한 64건은 모두 해당 문제의 실제 history에 존재하는 정수 목록을 사용했다.

즉, 이번 차이는 새 테스트를 더 돌리거나 코드를 다시 풀어서 생긴 성적 차이가 아니다. 다른 TRAIN 문제의 경험 설명을 유지한 상태에서, 저장된 `summary.trace_steps`와 `actions[*].step_no` 예시를 제공했을 때 제출 규약 준수가 높아졌다. 내부 추론을 읽었다는 주장은 하지 않는다.

공통 지시에는 `trace_steps`가 실제 기록을 가리켜야 한다는 설명과 placeholder가 있지만, 정수 목록·정렬·중복 금지 등의 검증 규칙을 완전히 명시하지 않았다. **따라서 여기서 확인된 것은 이러한 제출 안내 아래 형식 예시가 주는 효과**다. 완전한 형식 schema를 양쪽에 공통 제공한 경우의 추가 효과는 별도 실험이 필요하다. 다음 전체 문제풀이 비교에서는 이 공통 안내 조건을 구분해야 형식 보완 효과와 알고리즘 경험의 효과를 분리할 수 있다.

## 미확정과 실행 검증

KEEP의 `abc384_f` 반복 2, `abc382_f` 반복 3은 broker가 첫 요청을 받았지만 원시 요청을 저장하는 단계에서 실패했다. 원래 예외 종류는 generic 오류 처리로 기록되지 않았다. Windows text stdin의 CP949/surrogateescape와 UTF-8 직렬화의 충돌은 별도 합성 입력으로 재현했으며, 당시 두 실패의 정확한 예외를 직접 기록한 것은 아니다.

두 요청은 native STARTED/COMPLETED 이벤트에 동일하게 남아 있고, 그 요청을 원래 검증기로 사후 계산하면 형식·후보 보존 모두 통과한다. 이 보조 결과로 본 점수의 null을 대체하거나 재시도하지 않았다. 누락 2건을 모두 실패/모두 성공으로 두는 계획된 72건 기준 주 지표 범위는 **87.5~90.3%**이며 DROP은 0%다. 형식 통과율의 같은 범위는 88.9~91.7%다.

완료 후 1,551개 파일 참조를 검증했다. 원본·고정 입력은 변하지 않았고, 144개 native 세션은 모두 서로 달랐다. 저장된 141개 첫 요청은 native의 첫 STARTED/COMPLETED 요청과 정확히 일치했다. 추가 제출 시도·허용되지 않은 도구 사용·새 공개 테스트·비공개 채점·메모리 갱신은 모두 0건이다. 감사 상태는 두 기록 오류와 정상 미제출 1건을 명시한 `PROVENANCE_VALID_WITH_EXECUTION_FLAGS`다.

아래는 실행 전에 고정한 계획이다.

이 실험은 **같은 제출 직전 상태에서 L1의 형식 예시를 보여주는 것이 첫 제출 성공률에 영향을 주는지** 확인한다. 세션 전환과 추가 테스트를 양쪽에서 같게 고정한다. 전체 메모리 구조의 문제 해결률 효과나 기존 +41.7%p의 인과 분해를 측정하는 실험은 아니다.

## 고정 조건

- 대상: 이전 Luna VALID 24문제 전체. 성공으로 바뀐 사례만 선택하지 않는다. TEST 182문제는 사용하지 않는다.
- 모델: `gpt-5.6-luna`, reasoning `low`, 기존 Codex native 로그인 경로. 요청 모델 ID를 기록하며 백엔드 가중치 식별까지 보증하지 않는다.
- 24문제 × 2조건 × 3회 = 144개 독립된 새 세션. 문제당 반복 측정이며 144개의 독립 문제로 해석하지 않는다.
- 동시에 최대 2세션, 세션당 180초, 첫 `benchmark.action` 1회만 평가. 새 테스트·새 검색·수정 재시도·메모리 갱신·비공개 채점은 없다.
- 후보: 기존 OFF의 **첫 `finish` 요청에 담겼던 원본 코드**. 양쪽에서 바이트까지 같은 후보를 제출해야 한다. 당시의 `source_lesson`과 거절 응답은 제공하지 않는다.
- 공개 기록: 첫 `finish` 요청 STARTED 전에 완료되어 전달된 성공 작업 기록만 사용한다. 24문제 모두 그 기록과 당시 validator가 사용 가능한 기록이 일치한다.
- 공통 문맥: 당시의 L0 문맥, 문제·공개 예제·후보·공개 작업 기록. 제출만 남았다는 공통 지시를 추가한다. 따라서 이전의 전체 풀이 세션을 그대로 재현하는 실험은 아니다.
- 기억: 각 문제의 기존 ON에서 가장 먼저 주입된 TRAIN 경험 1개. 결과와 무관한 고정 규칙이다. 검색하지 않았던 `abc386_c`는 양쪽 입력이 동일한 무메모리 대조군으로 남긴다.

## 비교 조건

| 조건 | 제공하는 기억 |
| --- | --- |
| KEEP | 원래 경험의 모든 필드. 중첩 JSON도 공통 serializer로 정규화한다. |
| DROP | 같은 경험에서 `summary.trace_steps`, `actions[*].step_no`만 삭제한다. |

경험의 설명·알고리즘 교훈 등 다른 내용은 유지한다. 삭제된 자리에 잘못된 문자열이나 null을 넣지 않는다. 출처 해시와 변환된 view 해시는 구분한다. 처치는 **필드명·숫자 예시·입력 길이를 함께 바꾸므로** 숫자 값만의 효과로 해석하지 않는다. 두 조건의 실제 입력 바이트 수도 기록한다.

각 반복에서 문제 순서는 사전 고정 해시 순서이고 KEEP→DROP 12쌍, DROP→KEEP 12쌍으로 **실행 시작 순서**의 균형을 맞춘다. 두 작업자는 겹쳐 실행되므로 이는 한쪽이 끝나야 다음 조건을 시작하는 순차 실행을 뜻하지 않는다. 모델 실행용 작업 폴더 이름은 조건명이 드러나지 않는 해시 ID다. 모델의 무작위 seed는 고정하지 못하므로 실제 시작 시각과 순서도 기록한다.

## 판정과 분석

주 지표는 **첫 동작이 원래 제출 validator를 통과하고 고정 후보도 그대로 보존했는지**다. 형식 validator 통과, `trace_steps` 유효성, 후보 보존 여부도 따로 보고한다. 원래 validator가 허용하는 모든 성공 history 번호를 인정하며 공개 테스트 번호만으로 제한하지 않는다.

미제출·잘못된 동작·잘못된 형식은 실패다. 관측되지 않은 첫 동작을 알 수 없는 전송·인프라 오류로 잃은 경우 null로 남기며 실패와 합치지 않는다. 관측된 첫 동작은 이후 재시도로 덮어쓰지 않는다. 자동 재시도는 없다. 끝난 시도의 결과와 원본 입력 해시가 일치할 때만 재개 시 재사용한다.

조건별 성공 수/관측 수, 24문제별 3회 결과와 차이, 무메모리 대조군을 함께 보고한다. 차이의 불확실성은 문제 단위 cluster bootstrap(20,000회, seed 240924)으로 계산하며 탐색적 구간으로 해석한다. null이 있으면 양쪽 결과가 모두 관측된 반복쌍만 차이 계산에 쓰고 제외 수를 표시한다. 같은 문제의 3회 결과를 독립 문제로 늘려 잡지 않는다.

원래 세션에는 없던 공통 제출 전용 지시와 전체 공개 기록이 형식 힌트를 줄 수 있다. 두 조건이 모두 잘 제출하면 형식 예시의 추가 효과를 검출하지 못하는 천장 효과도 가능하다. 이 경우 개선을 꾸며내거나 조건을 사후 변경하지 않는다.
