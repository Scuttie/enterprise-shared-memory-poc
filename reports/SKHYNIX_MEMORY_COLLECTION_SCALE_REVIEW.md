# 메모리 경험 수집 규모 검토

상태: **설계 제안이며 현재 실행에 적용하지 않았다.** 기존 24개 학습·500개 평가의 고정 설정과 실행 기록은 유지한다. 아래 120·240·60이라는 수는 비교를 위한 제안이지, 충분한 경험량으로 검증된 임계값이 아니다.

현재 저장소당 두 문제, 총 24문제는 파이프라인의 초기 동작과 적은 경험에서의 전이를 관찰하는 규모로는 의미가 있다. 그러나 다양한 문제에서 PDF 구조의 효과를 판단할 주 실험으로 사용하려면 경험량과 유형의 충분성을 먼저 확인할 필요가 있다. 평가를 500개로 크게 해도 학습 bank의 빈약한 내용이나 적용 범위를 보완하지는 못한다.

점검 당시 공식 학습 완료는 17개, 수집 기록은 80개였다. 기록에는 한 문제의 여러 공개 테스트 시점과 subgoal 종료가 포함되므로 독립적인 문제 경험은 17개다. 당시 검증 스킬은 0개였지만 아직 reflection 전이므로 승격 실패의 증거로 해석하지 않는다.

현재 L3 검증은 같은 재사용 절차를 서로 다른 문제와 합성 소유자의 실제 공개 실패→구현 수정→동일 명령 성공 근거로 확인한다. 저장소당 두 문제는 이 최소 지원 조건과 같다. 두 문제가 서로 다른 절차를 요구하거나 하나에서 필요한 검증 기록이 나오지 않으면 대체할 다른 문제 조합이 없다. Django의 경우 학습 두 문제로 평가 231개의 다양한 영역에 도움을 주어야 한다. 여러 체크포인트가 있더라도 문제 종류의 다양성까지 늘어나는 것은 아니다.

권장 확장안은 다음과 같다.

1. 현재 24개를 초기 규모의 기록으로 보존하고 중복 풀이·성공 사례 선별을 하지 않는다.
2. 기존 24개를 포함한 **120개와 240개의 중첩된 학습 집합**을 미리 정한다. 추가 수집은 `gpt-6-astra / high`를 사용한다. 원래 8개 `ultra` 기록은 그대로 표기한다.
3. 500개 최종 평가와 겹치지 않는 후보에서 **별도 메모리 개발 검증 60개**를 먼저 분리한다. 이 60개는 학습 bank에 넣지 않는다.
4. 동일한 개발 검증 집합에서 기준선과 24·120·240개 기반 bank의 해결률, 유효 메모리 전달률, 시간·요청 수를 비교한다. 기준선 실행은 같은 조건으로 한 번 수행해 공통 비교에 사용한다. bank가 원래의 필수 L3 검증 요건을 충족하지 못하면 `NOT_READY`로 기록하며 요건을 낮춰 전체 PDF 구조 조건으로 표시하지 않는다.
5. 경험 수·유형·검색 규칙을 개발 검증 단계에서 결정한 뒤 고정하고, 최종 Verified 500개를 A/C 각각 한 번씩 평가한다. 최종 500개의 성패를 보고 학습 문제나 교훈을 고르지 않는다.

규모 증가와 함께 공개 문제 설명 기준으로 수정 유형·관련 하위 시스템을 나누어 수집한다. 예를 들어 예외 처리, 직렬화, 배열·타입 동작, API 호환성 등 서로 다른 유형을 포함하면서, 유형 안에서는 서로 다른 문제의 반복 근거가 생기도록 구성한다. 실제 정답 패치나 최종 평가의 성패는 선택에 사용하지 않는다. 공개적으로 매우 유사한 중복 문제군은 학습·개발 검증 사이에 나뉘지 않도록 확인한다. 숫자만 늘려 검증되지 않은 교훈을 쌓는 방식은 피한다.

현재 비중복 후보 1,786개 안에서 아래 배분은 문제 수 기준으로 가능하다. 개발 검증 후보를 먼저 확보하므로 후보가 10개뿐인 Flask는 학습 6개·개발 검증 4개로 나눈다. 실제 ID와 문제군 분리는 별도 고정 목록으로 검증해야 하며, 아직 새 목록을 등록하거나 추가 문제의 실행 환경을 준비한 상태는 아니다.

이 배분은 개발 검증 저장소당 최소 4개를 먼저 배정하고 나머지를 후보 수에 비례해 배분한 뒤, 남은 학습 후보에 저장소당 최소 10개를 우선 배정하는 방식이다. 후보가 부족한 Flask는 학습 6개로 제한한다. 기존 24개는 학습 집합에 반드시 남긴다. 큰 저장소의 추가 경험과 작은 저장소의 최소 범위를 함께 확보하기 위한 제안이며, 최적 배분으로 검증된 것은 아니다.

충분성은 총 기록 수만으로 판단하지 않는다. 저장소·유형별 고유 학습 문제 수, 검증 절차를 지지하는 서로 다른 문제 수, L1/L2/L3의 실제 유효 전달률과 개발 검증 해결률을 함께 확인한다. bank가 커져도 현재처럼 주입 예산을 제한하고, 늘어난 기록은 여러 reflection 작업으로 나누어 원본 근거를 보존해야 한다. 수집 수만 바꾸고 현재의 24개 전용 등록·검증·reflection 한도를 그대로 사용해서는 안 된다.

점검 시 완료된 `high` 9문제의 평균 전체 실행 주기는 약 11.6분이었다. 같은 속도로 24→120의 추가 96개 수집은 약 19시간, 24→240의 추가 216개 수집은 약 42시간이다. 이는 추가 수집만의 시간이며, reflection·검증과 개발 검증 풀이 시간은 별도다. 60개 개발 검증을 기준선과 최대 세 bank에서 모두 수행하면 최대 240회 풀이로, 같은 속도에서 약 46시간이 추가된다. 문제 구성과 실행 환경에 따라 달라진다.

경험의 다양성과 성공·실패 기록에서 재사용 가능한 전략을 추출하는 품질을 함께 고려한다는 방향은 [ReasoningBank 논문](https://arxiv.org/html/2509.25140v2)의 경험 확장 연구와도 관련된다. 이 논문은 다른 방식의 온라인 경험 학습을 다루므로, 본 실험에서 120개나 240개가 충분하다는 근거로 사용하지 않는다.
