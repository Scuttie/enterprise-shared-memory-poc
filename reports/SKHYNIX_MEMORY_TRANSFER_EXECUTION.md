## 1. LCB 개인 L3 전이: LCB004

이전 LCB003은 명시적인 제출 규칙 아래 OFF 24/24, ON 22/24였으며 실제 기억 주입은 L1뿐이었다. 새 실험은 별도의 코드·문제·저장소로 진행한다. 이전 결과, 은행, 구현 파일을 수정하지 않는다.

L3는 PDF 42쪽의 개인용 절차 범위다. 조직 공유 Gate B의 사용자 요건을 변경하거나 세션을 다른 사용자로 계산하지 않는다. 이번에 검증하는 것은 **모델이 작성한 기대 출력에 대해 실제 실행된 테스트 절차의 다른 문제 적용**이다. 알고리즘 의미, 기대 출력 자체의 정답성, 조직 전체의 재사용성까지 인증하는 것은 아니다.

| 단계 | 문제 수 | 실행 조건 | 예정 풀이 수 |
| --- | ---: | --- | ---: |
| TRAIN 발견 | 80 | 기억 없는 신규 풀이 | 80 |
| TRAIN 검증 | 40 | 발견 단계의 동결된 후보 절차를 배정 | 40 |
| VALID | 60 | OFF / ON / L1ONLY 각각 1회 | 180 |
| TEST | 182 | OFF / ON 각각 1회 | 364 |
| 합계 | 362개 고유 문제 | 준비 조건을 충족할 때만 후속 단계 진행 | 최대 664 |

문제 ID와 순서는 [고정 계획](../configs/skhynix_v1/lcb_004_transfer_plan.json)에 저장한다. TRAIN 발견·검증은 문제와 family가 서로 겹치지 않고, 이전 TRAIN 및 인프라 대조군의 family를 제외한다. VALID는 이전 24개와 문제 ID가 다르고 난도별 20개다. 다만 60개 중 29개는 이전 VALID 문제와 family가 같으므로 완전히 새로운 family의 평가라고 주장하지 않는다. TEST 182개는 원래 분할을 그대로 유지한다.

모델은 `gpt-5.6-luna`, reasoning `low`, 동시 실행 2개, 문제·조건당 1회다. 각 풀이의 한도는 600초, 도구 호출 24회, 세션 4개, 코드 65,536B, prompt 196,608B, L0 문맥 48,000B, 기억 12,000B다. 기존 공개 테스트와 새 생성 테스트가 **총 4회 실행 예산을 공유**한다. 모든 평가 조건에 같은 도구와 명시적인 제출 규칙을 제공한다.

### 관측 가능한 개인 절차

추가 `run_command` 도구는 셸 명령을 받지 않는다. 전체 후보 코드, 2~12개 입력·기대 출력, `boundary_cases` 또는 `differential_cases`라는 모델의 전략 설명, 근거, 선택적 절차 ID만 받는다. 동일한 공식 공개 실행기로 실제 코드를 실행하며, 기대 출력은 `MODEL_GENERATED_EXPECTATIONS`로 표시한다. `differential_cases`라는 이름만으로 독립 참조 구현의 검증이 이루어졌다고 주장하지 않는다.

후보 절차가 되려면 발견 문제에서 실제 생성 테스트의 assertion RED → **동일 입력·기대 출력에서 변경된 코드의 GREEN** → 같은 최종 코드의 원래 공개 예제 GREEN 순서를 만족해야 한다. 모델이 제출한 경험의 trace가 실제 RED/GREEN을 인용해야 한다. 실패를 만들기 위한 가짜 후보·stub은 허용하지 않는다. 정확한 코드·테스트·도구 출력 해시와 native 실행 이벤트로 증거를 연결한다.

검증 40문제에는 후보 ID 정렬 순서의 round-robin 배정을 미리 적용한다. 절차 ID는 실행 전에 지정되고, 모델은 적용 불가능하다고 판단할 수 있다. 별도 family의 문제에서 그 ID를 명시한 생성 테스트 GREEN 및 동일 최종 코드의 공개 예제 GREEN이 관측돼야 개인 L3로 승격한다. 원래 문제의 코드·입력값을 다른 문제의 답으로 주입하지 않는다. 절차 설명의 의미 자체는 모델 작성 내용으로 남고, 검증된 범위는 실행 패턴이다.

### 준비 판정과 평가

- 발견 후 후보가 0개면 검증·VALID·TEST를 실행하지 않고 `NOT_READY`로 보고한다.
- 검증 후 승격된 개인 L3가 0개면 VALID·TEST를 실행하지 않는다.
- 위 경우에 성과가 나올 때까지 TRAIN을 임의로 늘리지 않고 별도 DevEval 단계로 진행한다. 이미 실행한 TRAIN의 정답률은 사후 채점해 별도로 보고한다.
- 준비된 최종 은행은 VALID 전에 동결한다. VALID/TEST로 은행을 쓰거나 승격하지 않는다.
- 주 비교는 OFF와 ON이다. VALID의 L1ONLY는 더 많은 L1 경험과 L3 추가 효과를 구별하는 보조 비교다.
- ON은 적용 가능한 L3 → L2 → L1 순서로 조회한다. L2는 여전히 후보 코드에 한정되며, 조회 실패를 숨기기 위해 강제 주입하지 않는다.
- 단계별 모든 풀이가 봉인된 뒤 공식 숨겨진 테스트를 채점한다. 비공개 테스트와 채점 결과는 풀이 도구·기억에 전달하지 않는다.
- 주 성적은 정상 제출과 공식 정답을 모두 만족한 비율이다. 모델·규약·예산 실패는 실패, 확인되지 않은 인프라 결과는 null로 남긴다. 부분 실행을 자동 재시도하지 않는다.

별도로 후보·승격 절차 수, 검색 가능 수, 실제 주입 수, 명시적 적용 수, 적용 후 공개 검증 성공 수, 문제별 정답·시간·토큰을 기록한다. 기억이 저장돼 있다는 사실만으로 작동·효과를 주장하지 않는다.

## 2. DevEval 실행 확인

공식 [seketeam/DevEval](https://github.com/seketeam/DevEval)의 고정 revision을 사용한다. 기존 Linux/WSL에서 별도의 Python 3.9.18 환경을 만들어 공식 평가기를 실행한다. Docker 설치·실행은 하지 않는다. 모델 결과를 보기 전에 메타데이터 기준으로 여러 저장소의 cross-file 문제 10개를 선택한다.

원래 정답 구현의 테스트 통과, 의도적인 assertion 오답의 실패, 각 평가 뒤 정확한 소스 복원을 대조군으로 확인한다. 공식 평가기는 대상 함수 본문을 교체하므로, 각 실행에 별도 저장소 사본을 쓰거나 같은 저장소에서 직렬 평가한다. 환경에 의해 제외한 문제는 이유와 함께 공개하며 좋은 점수만 남기는 선택을 하지 않는다.

## 3. 저장소 L2/L3 비교와 사내 재현

DevEval 실행 확인 후 공개 저장소 스냅샷에서 L2의 함수·클래스·의존관계를 생성하고, 문제별 정답 본문과 채점 전용 정보가 모델/KG에 섞이지 않도록 분리한다. OFF와 ON의 소스 열람 권한 및 도구 예산은 같다. 주 비교는 전체 구조 ON/OFF이며 L2 또는 L3를 제거한 보조 조건으로 계층 기여를 확인한다. 정확한 대상·분할·조건은 모델 실행 전에 추가 고정한다.

사내 GLM용 패키지에는 같은 문제 ID·원본 해시·분할, 환경 준비 자료, vLLM 주소·모델명 설정, 경험 수집/은행 동결/평가 명령을 포함한다. GLM은 동일 TRAIN으로 자기 경험을 수집하도록 하며, Luna 은행을 그대로 쓰는 모델 간 전이는 별도 조건으로 구분한다. 여기서 GLM 결과를 생성하거나 사내 실행이 완료됐다고 표시하지 않는다.
